# ADR-0010: servidor MCP local sobre los artefactos empaquetados

## Contexto

El spec (§2, opción D) pide que un cliente de IA (Claude Desktop, Claude Code, Cursor) pueda preguntar a `ventaja` en lenguaje natural. La inteligencia la pone el cliente del usuario: el repo no lleva ni pide API keys, y debe funcionar desde un clon limpio con solo `uv sync`, igual que la pizarra (ADR-0009).

La tentación es hacer un espejo de la CLI, un tool por subcomando. Son unos quince que el cliente no sabe combinar, y las respuestas sin número ni titular redactado obligan al cliente a calcular o a inventar.

## Decisión

**Seis herramientas de lectura, no una por comando de la CLI.** `list_games`, `rank_players`, `player_profile`, `find_shots`, `explain_shot` y `what_if`. Cubren las tres conversaciones del diseño (ranking por equipo y reloj, el peor tiro de un jugador con su mejor alternativa, y mover a un jugador y revalorar) más la ficha. Toda salida es JSON de modelos pydantic (`mcp/models.py`), con los ids siempre junto a su nombre, los flotantes a 3 decimales y los titulares ya redactados. Más un recurso, `ventaja://glossary`.

**Stdio, sin HTTP ni autenticación.** `ventaja mcp serve` arranca un servidor local para una persona. Dependencia de ejecución nueva: `mcp>=2.3` (en 2.x `FastMCP` es `MCPServer`).

**Capa de servicio sin `mcp`.** `mcp/service.py` son funciones puras que devuelven modelos pydantic y no importan `mcp`; es lo que prueban los tests y lo que llama la CLI. `mcp/server.py` es fino: valida, llama al servicio y traduce `VentajaError` a error de herramienta con el mensaje tal cual, nunca una traza. Los parámetros comparten un único alias `Annotated` entre el despachador y los envoltorios MCP, y un test de paridad lo fija (ruling R2). El gemelo de shell, `ventaja mcp call TOOL [JSON]`, pasa por el mismo `call_tool`; `ventaja mcp tools` lista las herramientas con su esquema. Así el servidor se prueba en CI sin cliente de IA.

**Artefactos resueltos como la pizarra.** Cada tabla sale de la build si esta la tiene y, si no, de la copia empaquetada (`artifact_dir`). Una build parcial mezcla fuentes: decisiones de un partido con fichas de diez. Los pasos de CI que llaman al MCP corren con `VENTAJA_BUILD_DIR` vacío para leer siempre lo empaquetado.

**`games.parquet`.** La fecha, los equipos y el marcador solo estaban en `matches.json` y `meta/`, que no se empaquetan. `ventaja player build` escribe ahora `artifacts/games.parquet` (un partido por fila) junto a `players.parquet` y `teams.parquet`; `list_games` lo lee y `find_shots` saca de él el rival. Va versionado, y `data/people.py` comparte la resolución de nombres con la pizarra.

**Reglas de entrada.**

- `player` y `team` aceptan un id o un trozo del nombre, sin distinguir mayúsculas ni acentos. Si no casa o es ambiguo, el error lista los candidatos (`id — name — team`) y nunca elige por el usuario. Las listas de jugadores se limitan a 20, ordenadas por nombre, con «… and N more» (ruling R1); las de equipos salen siempre completas (17).
- `min_shots` vale 1 por defecto, como `player rank`. Cada fila lleva su `n`, y el campo `caution` avisa cuando hay menos de `PROFILE_MIN_SHOTS` = 8 tiros legibles.
- `clock` (`24-14`, `14-6`, `6-0`) solo se combina con `by = mean_cost`: las fichas guardan el coste por tramo, no la lectura ni el retraso. Con otro `by` es un error con ese mensaje, y el servidor no reagrega decisiones.
- `limit` vale `MCP_DEFAULT_LIMIT` = 10 por defecto y `MCP_MAX_LIMIT` = 50 como máximo, ambas en `value/params.py`.

**`what_if` hereda el ADR-0009.** Jugador movido con velocidad 0, el balón sigue al tirador, tirador movido valorado por geometría, recorte a la media pista de ataque y máximo `BOARD_MAX_MOVES` = 10 movimientos. Reutiliza `Board` y, por él, `decide_snapshot`, que sigue siendo el único punto de entrada de valoración. La respuesta devuelve la posición efectiva para que se vea el recorte. Un `player` fuera de los diez del frame es un `VentajaError` que los lista.

**Glosario como plantilla.** `mcp/glossary.md` es una `string.Template` que se rellena al servirla con los valores importados de `value/params.py`, de modo que ningún número del glosario se copia a mano.

**Prueba con cliente real.** Claude Code (`claude -p --mcp-config`) descubre las seis herramientas desde la rama; la evidencia está en `docs/review/2026-11-mcp/`.

## Consecuencias

El repositorio crece unos cientos de bytes (`games.parquet`). A cambio, el servidor funciona desde un clon limpio y sin API keys. Orden de regeneración: el de ADR-0009, y `player build` escribe también `games.parquet`. Las constantes `MCP_DEFAULT_LIMIT` y `MCP_MAX_LIMIT` cambian solo con un ADR.

**Límites conocidos.**

- Una build parcial mezcla fuentes y puede dar resultados incoherentes entre herramientas.
- Todo lo de la pizarra: la defensa no reacciona, un jugador colocado tiene velocidad 0 y los movimientos lejos de lo visto extrapolan.
- Solo hay 10 partidos con tracking: el cliente debe decir que alguien no está, no suplirlo (el glosario se lo recuerda).
- Con `min_shots = 1` entran jugadores con un solo tiro; la señal de cautela es `n` y `caution`, no el filtro.
- No hay clips ni figuras: `explain_shot` devuelve `clip_command`, el comando de la CLI que los produce (necesita la build).
- La respuesta la redacta el cliente: el servidor garantiza las cifras, no el texto.

**Alternativas descartadas.**

- *Un tool por comando de la CLI.* Quince herramientas sin combinación obvia, con la lógica repartida.
- *Una herramienta de SQL libre.* Necesita la build y abre la puerta a respuestas sin método.
- *Transporte HTTP.* Añade autenticación y exposición de red a una herramienta local.
- *Un LLM dentro del servidor.* Exigiría una API key (anti-objetivo del spec) y mezclaría el método con la redacción.
